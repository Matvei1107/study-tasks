# Задача №3. Очередь с приоритетом — вариант 6: «Таймеры с переносом и отменой»

Своя бинарная куча на массиве (без `heapq` и готовых куч) и решение на ней
варианта 6 из методички.

## Условие варианта

Обрабатываются команды:

| Команда | Смысл |
|---|---|
| `SET <id> <at>` | назначить таймеру `id` момент `at`; прежнее назначение того же `id` заменяется |
| `CANCEL <id>` | отменить активный таймер; отсутствующий `id` игнорируется |
| `ADVANCE <to>` | продвинуть модельное время до `to` и выдать сработавшие таймеры |

Правила:
- начальное время `0`; `at >= текущего времени`, `to` не убывает;
- `SET` сам по себе таймер не запускает — срабатывание делает только `ADVANCE`,
  причём граница `to` включается (`at <= to`);
- сработавшие выдаются по моменту срабатывания, при равенстве — по порядку назначений;
- сработавший или отменённый `id` можно назначить заново;
- конец входа время не продвигает.

## Своя бинарная куча (`binary_heap.py`)

Данные лежат в обычном списке, индекс `0` — вершина. Сравнение идёт через
`key` и флаг `min_heap`, поэтому одна и та же реализация даёт и min-, и
max-кучу, и произвольный порядок:

```python
BinaryHeap(min_heap=True)                       # обычная min-куча
BinaryHeap(min_heap=False)                      # max-куча
BinaryHeap(min_heap=True, key=lambda a: (a.at, a.seq))   # как в варианте 6
```

Операции и сложности:

| Операция | Что делает | Сложность |
|---|---|---|
| `push` | добавить элемент | O(log n) |
| `pop` | убрать и вернуть вершину | O(log n) |
| `peek` | вершина без удаления | O(1) |
| `replace_top` | заменить вершину и восстановить кучу | O(log n) |
| `heapify` | построить кучу на месте | O(n) |
| `size` / `is_empty` | размер / пустота | O(1) |
| `check_invariant` | проверка свойства кучи (для тестов) | O(n) |

`heapify` просеивает вниз от середины массива к началу: у листьев детей нет,
поэтому достаточно `n/2` просеиваний, что даёт O(n) вместо n вставок.

## Логика таймеров (`timers.py`)

- назначения хранятся в min-куче, упорядоченной по `(at, seq)`;
- активные таймеры — в обычном словаре `id -> назначение`;
- `seq` — уникальный номер назначения. Он решает сразу две задачи: задаёт
  порядок при равных `at` и позволяет понять при извлечении, устарела ли запись.

```python
def advance(self, to):
    self._time = to
    fired = []
    while not self._heap.is_empty() and self._heap.peek().at <= to:
        assignment = self._heap.pop()
        if self._active.get(assignment.timer_id) is assignment:
            del self._active[assignment.timer_id]
            fired.append((assignment.timer_id, assignment.at))
    return fired
```

### Ленивое удаление

При переносе (`SET` по существующему `id`) или `CANCEL` старая запись физически
из кучи не убирается. Она остаётся там и в словаре активных на неё уже никто не
ссылается. При извлечении мы сравниваем запись из кучи с текущим активным
назначением **по ссылке** (`is`): если это не тот же объект — запись устарела и
просто выбрасывается. Вместо ссылки можно было бы сравнивать `seq`, смысл тот же.

Так не нужно ни искать запись по `id`, ни перестраивать кучу, а `SET` и `CANCEL`
остаются O(log n) и O(1).

### Граница и порядок

Условие выхода из цикла — `at <= to`, то есть момент `to` включается: таймер,
назначенный ровно на `to`, срабатывает. `SET` ничего не запускает сам, поэтому
таймер, назначенный в текущий момент (`at == time`), сработает на ближайшем
`ADVANCE`, а не сразу.

Порядок выдачи задаёт сама куча: она упорядочена по `(at, seq)`, поэтому
элементы извлекаются уже в нужном порядке — сначала по времени, при равенстве
по порядку назначений.

### Размер кучи и устаревшие записи

В куче лежат все назначения, включая устаревшие, поэтому

```
heap_size = active_count + stale_count
```

`heap_size` растёт на каждый `SET` и уменьшается только при извлечении в
`ADVANCE`. Это осознанный компромисс ленивого удаления: освобождение памяти
откладывается. В длительно работающей системе такие записи стоило бы
периодически вычищать (перестроить кучу по словарю активных). Методы
`heap_size()` и `stale_count()` добавлены как раз чтобы это видеть и
тестировать.

## Сравнение с эталоном

Эталон из методички — словарь активных назначений, а при `ADVANCE` фильтрация
по `at <= to` и сортировка. Обозначим `m` — число активных таймеров, `k` —
сколько сработало, `s` — сколько устаревших записей вынуто при этом `ADVANCE`.

| | своя куча | эталон (dict + сортировка) |
|---|---|---|
| `SET` | O(log n) | O(1) |
| `CANCEL` | O(1) | O(1) |
| `ADVANCE` | O((k + s) log n) | O(m log m) |
| память | O(всех назначений) | O(m) при чистом словаре |

Ключевое отличие — `ADVANCE`. Эталон каждый раз перечитывает **все** активные
назначения и сортирует их, даже если готовых к срабатыванию единицы. Куча же
отдаёт только те, что реально вызрели, за счёт O(log n) на каждое извлечение.
На редких `ADVANCE` с большим числом активных таймеров это заметно выгоднее.
Платой служит память: устаревшие записи не удаляются сразу, поэтому куча может
быть больше числа активных таймеров. При частых переносах одного и того же
`id` в куче накапливается «мусор», который уходит только при `ADVANCE` за его
момент.

## Формат входа и выхода

Вход — JSONL, по одной команде на строку:

```json
{"cmd": "SET", "id": "a", "at": 5}
{"cmd": "CANCEL", "id": "a"}
{"cmd": "ADVANCE", "to": 10}
```

На каждый `ADVANCE` в стандартный вывод печатается JSON-массив сработавших
таймеров в виде `[id, at]`:

```
[["b", 3], ["a", 5]]
```

## Что покрыто тестами

Куча: порядок min/max, `peek` без удаления, размер и пустота, исключения на
пустой куче, `replace_top` для min и max, `heapify` (валидность, сохранение
элементов, пустой и одноэлементный вход), проверка инварианта после серии
случайных операций, кастомный ключ, порядок при равных ключах, дубликаты.

Таймеры: happy path, «`SET` не срабатывает сразу», включение границы, перенос на
более ранний и более поздний момент, отмена и отмена несуществующего `id`,
повторное использование `id` после отмены и после срабатывания, равные времена и
порядок назначений, `ADVANCE` без событий, время назад, учёт размера кучи с
устаревшими записями, а также сверка с эталонной реализацией на случайных
потоках команд.

## На что смотреть на защите

- почему устаревшие записи можно не удалять и как они отсеиваются (`is`/`seq`);
- почему `ADVANCE` использует `<= to`, и как связаны «сработал на границе» и
  «`SET` не срабатывает сразу»;
- почему куча может быть больше числа активных таймеров и когда это проблема;
- почему в цикле `ADVANCE` нельзя останавливаться раньше (устаревшая запись
  сверху не значит, что ниже нет валидных с таким же `at`).
